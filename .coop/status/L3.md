## L3 — round 5: RLS policy hardening (074) + the architectural landmine it exposed
**Residual from SEC-1 closed, and a bigger finding surfaced behind it.**
- **The defect**: 94 policy predicates inlined `current_setting(...)` themselves in three shapes with TWO failure behaviours — `(current_setting('schoolos.tenant_id', true))::uuid` raised **22P02** on an empty-string GUC, and `current_setting('schoolos.tenant_id')` (no missing_ok) raised **42704** when the GUC was never set. So the SAME "no tenant context" state denied on most tables and hard-errored on others, and one state could 500 an entire request. **An authorization predicate has exactly two acceptable outcomes: visible or not visible. It must never be able to fail the query.** 074 routes every predicate through `app.current_tenant()` / `app.current_user_id()` (NULLIF(null-or-empty) → NULL → deny). Live-verified: empty GUC → 0 rows (was 22P02), unset GUC on a previously-42704 table → 0 rows, real tenant → 375 students (no regression). Quantified: **34 predicates carried the 42704 hole, 60 the 22P02 hole.**
- **My own migration was buggy first, in exactly the class this doc is about.** It looped `FOR r IN SELECT ... FROM pg_policy` and issued `ALTER POLICY` inside that loop — mutating the catalogue rows being scanned, so PostgreSQL **skipped rows**: it silently hardened 44 of 94 predicates and reported success. The tell was a *discrepancy between two databases* (freshly migrated showed 50 remaining; migrated in two passes showed 0). Fixed by materialising the candidate list into a temp table first, plus an explicit `RAISE EXCEPTION` if candidates ≠ rewritten, so a partial hardening can never again report success. Also fixed a `RAISE WARNING` with 4 `%` placeholders and 3 arguments.
- **The bigger finding (worth more than the fix): `scripts/seed.js` replays 35 migration files at runtime, and that replay UNDOES policy hardening.** Measured step by step on one database: `after migrate → inline=0`, `after bootstrap → inline=0`, `after seed → inline=50`. The replay re-creates the policies from migrations 009–048, and those files write inline `current_setting`. **So migration 074 could never hold in any seeded environment — i.e. in every test and every demo.** And because `migrate.js` refuses to run once a recorded migration's checksum drifts, the old migrations CANNOT be corrected at source. Fix: the seed re-applies 074 after the replay (idempotent), with the rule written down — anything that hardens/replaces a policy from those migrations must be re-applied there too, or the seed silently reverts it. Regression pin: `tests/rls-policy-hardening.test.js` asserts **no policy anywhere inlines current_setting**, and fails when that seed block is removed (verified: 4/6 → 6/6).
- **Helpers return TEXT, not uuid — deliberately.** The first attempt returned uuid and the migration died with `operator does not exist: text = uuid`, because some predicates compare `tenant_id::text = current_setting(...)`. Substituting an expression of the SAME TYPE keeps every existing cast and comparison meaning exactly what it meant, so the only behavioural change is the closed hole.

## L3 — round 8: SEC-21 CLOSED — payment webhooks verify before touching anything payload-driven

### Two independent live defects, both fixed
1. **Pre-authentication oracle (the P0).** The razorpay handler built its HMAC candidate list as

## L3 — round 11: PRD-13 part 1 CLOSED — a sandbox carrier is no longer recorded as a delivery

## Round 31 — DAT-3 CLOSED (the delivery stage had no gauge) + a full-suite run delegated
Register row, reframed: *"the relay's only subscriber performs NO delivery, yet the row is stamped
`processed_at`, and the ONE queue gauge in the system is built on exactly that column."*

### I re-read the code before trusting that framing, and the framing was wrong in an instructive way
`processed_at` is **not** a lie. It marks that the relay finished *its own* deliverable, which for the log relay
is emitting the event to the log sink — stdout, collected by the operator's log pipeline. That is a real
delivery to a real sink. The earlier reading ("the metric says delivered for events that were only logged")
conflates two different sinks, and `scripts/outbox-worker.js:62-66` had already conceded as much in a comment.

**The defect is narrower and worse: the stage AFTER the relay had no reader at all.** The webhook fan-out keeps
its state in `app.webhook_deliveries` with its own retry and DLQ — and nothing read it: not a gauge, not the
health probe, not an alert. The one check that mentions webhooks (`webhook_undiscovered`) reads
`app.outbox.discovered_at`, so it answers only "did the fan-out SCAN this event" and is **structurally blind** to
an event that was scanned, queued for a paying subscriber, and never delivered. So the reachable production
failure is: every subscriber delivery failing while the only queue signal reads `outbox_pending 0` — a clean,
drained, healthy-looking queue. Measured on dev: `outbox_pending 2`, `webhook_subscriptions 0`,
`webhook_deliveries 0` — the blind spot was real and empty precisely because nothing could see it.

### What I changed
- `src/app.js`: three gauges, deliberately not one, because collapsing them is what created the blind spot —
  `schoolos_webhook_deliveries_queued` (the fan-out is stuck), `_failed` (a subscriber never got its event),
  `_stalled` (queued, due, and unretried over 10 minutes → the worker is wedged or not running). Plus a `HELP`
  line on `outbox_pending` stating what it actually measures, since misreading it as a delivery count is what
  hid this for so long.
- `scripts/health-probe.js` + `ops/alerts/schoolos.rules.yml`: new check and rule `webhook_undelivered`,
  reading the same state. The existing `ops-deploy` test asserts every rule has a check and every check has a
  rule, and it stayed green (24/24) — the wiring is machine-checked, not eyeballed.
- `tests/dat3-delivery-visibility.test.js`, **6/6**. The headline test is the regression itself: it drains the
  outbox to a clean `outbox_pending 0` and *then* fails a delivery, asserting the outbox still reads 0 while the
  failed count reads 1 — the exact state in which the old signal said all was well. It also asserts the alarm
  does not cry wolf (a delivery with a retry scheduled in the future is backlog, not a stall), and that an
  unreadable signal comes back `skipped` rather than a fabricated zero.
- **Mutation-probed:** disabling the gauge emission fails 4 of the 6 tests. Restored and re-verified 30/30
  across both files.
- Verified on the real dev database: `/metrics` returns all three gauges, and the OPS-17 duplicate-series check

number only resets the clock.

Three properties I insisted on, each of which is a mistake this project has already made:
1. **It writes the artifact even when the suite is RED.** A generator that only runs on success produces an
   artifact whose mere existence implies green — a false green with extra steps, and it deletes the failure
   evidence. The artifact records the exit code and the failure set, and the script exits non-zero.
2. **It never invents a number.** Counts come from the runner's summary, the filesystem, or the live database; a
   count it cannot obtain reads **UNMEASURED**, never omitted and never guessed. Reading an existing log (so
   `--no-run` does not pretend to have just run anything) honestly reports exit code UNMEASURED.
3. **It stamps the revision.** Coop law forbids `git` here, so the fingerprint is a sha256 over the tracked
   source files (280 files) — that is what ties the numbers to a tree, and if it stops matching, the numbers are
   history rather than state.

**Two bugs I introduced in it, both of which produced exactly the defect the artifact exists to prevent:**
- Version 1 looked for TAP's `not ok N - name`. This reporter never emits it, so the artifact printed
  **"Failures (0)" over a log containing 7 failures** — a false green emitted by the anti-false-green tool. I
  noticed only because I pointed it at a *known-red* log instead of a green one, which is the whole reason to test
  a reporting tool against a red input.
- Version 2 fixed that and then extracted **1 of 7**, because it required the `(12.3ms)` timing suffix and some
  failure lines carry none (a test that dies in a `before` hook).
The durable fix is not either regex: it is the **reconciliation check** — the artifact compares its own parse
against the runner's tally and, when they disagree, prints that the list is incomplete. Which is how I discovered
the limitation is structural rather than mine: the reporter renders a **cancelled** test identically to a failed
one (both `✖`), so no name list from this output can be reconciled. Rather than ship a confidently-wrong list, the
artifact now labels the names **PARTIAL**, names the run log as authoritative, and states that the limitation is
recorded deliberately because **an under-reporting failure list reads as completeness.**

Also recorded while measuring: `npm test` uses `--test-timeout=60000` while CI uses `120000`. Different timeouts
