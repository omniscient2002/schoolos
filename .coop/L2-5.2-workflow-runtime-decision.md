# L2-5.2 — Workflow runtime: DECISION (Wave 5, D-36 GO)

**Decision:** implement the **minimal honest step-runner**, riding the existing
`app.outbox` event spine. No workflow UI is authorized (S0's ruling: UI copy is
deleted unless the runner ships with full tests — the runner + tests are this
delivery, so the UI door stays closed until L5 pairs on it).

## What exists today (the hooks we ride)
- `app.outbox` (001/042): every meaningful state change publishes a row
  `(tenant_id, topic, payload, created_at)` — the delivery spine the webhook
  worker (L2-4.1) and comms dispatcher already consume.
- `app.webhook_subscriptions` / `app.communications`: existing outbound surfaces.

## The minimal step-runner (what ships)
- **Table** `app.workflow_rules` (071): one rule = `{tenant_id, name, topic,
  condition jsonb, action jsonb, enabled}`.
  - `condition` (optional): `{field, op, value}` with `op ∈ exists | equals |
    contains` evaluated against the outbox payload's TOP level only. No
    expressions, no scripts — a small, auditable vocabulary.
  - `action` (v1): `{kind: 'outbox', topic, payload}` (fan-out to a derived
    event) or `{kind: 'comms', channel, template, body}` (enqueue a message
    into `app.communications` with the standard dedup key
    `wf:<ruleId>:<eventId>`). Nothing else — no HTTP calls (webhooks already
    exist), no plugins invoked, no chains (a rule's output is NOT re-triggered;
    enforced by skipping topics with the `wf:` prefix in the dedup key).
- **Runner** `server/scripts/workflow-worker.js`: claims outbox rows (SKIP
  LOCKED, same pattern as the webhook worker), evaluates enabled rules of that
  tenant for that topic, writes the action rows, marks the outbox row
  workflow-processed. Idempotent per (rule, event) via the dedup key UNIQUE
  constraint. Exports `runWorkflowPass(c)` for tests + the day-worker.
- **Doors** (owner/itadmin, audited): `GET /workflow-rules`,
  `POST /workflow-rules`, `DELETE /workflow-rules/:id`. No UI yet — L5 pairs
  when ready; copy stays honest ("rules apply to new events only").

## What deliberately does NOT ship (post-run backlog)
- Chained workflows, loops, conditions across joins, per-step retries UI,
  workflow analytics, third-party triggers. The runner is a filter+actuator on
  ONE spine, not an engine.

## Honesty ledger
- No workflow fiction anywhere: the runner only acts when a rule row exists,
  and every action row is visible in the same tables staff already read
  (outbox / communications). Failures park as the outbox relay's own DLQ
  semantics (status='failed' + last_error), never silently dropped.
